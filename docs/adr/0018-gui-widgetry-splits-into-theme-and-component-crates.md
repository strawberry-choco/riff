# The Frontend Widgetry Splits Into a Theme Crate and a Component Crate

**Status**: Accepted
**Date**: 2026-10-15

`riff-gui` holds four kinds of code in one crate — the design authority (the token store, `fonts`, `icons`), the presentation primitives, the feature composites, and the host adapters — and the line between the first two and the rest was held by a source-string sweep over twelve *file names* rather than by the compiler. The sweep is weaker than it looks: it forbids seventeen names, `riff_backend` is not one of them, and three modules the architecture doc itself calls primitives (`menu`, `feedback`, `artwork`) name business types and pass. For clean architecture, and for a frontend whose file count keeps rising, the widgetry is extracted into two crates that no business crate can reach: **`riff-gui-theme`** — the design authority, holding the palette and token store, the vendored fonts and the icon set, and the `assets/fonts` + `assets/icons` those two are compiled from — and **`riff-gui-components`** — the presentation primitives, on the props-in / responses-or-typed-intents-out contract. `riff-gui` keeps the feature composites and the host adapters, and depends on both. This amends the "Inside `riff-gui`: the internal component layer" section of `docs/technical/architecture.md`, which had decided the widgetry stays an internal three-tier layer "until a second consumer, a publication need, or a measured independent-build need appears". Those three triggers stand and are not retired; the decision is taken for a fourth reason the doc did not name — a boundary the *compiler* enforces, on a growing crate, rather than a substring test on a list of file names.

## Considered Options

- **Keep the internal three-tier layer (the status quo).** Costs nothing to keep and the token sweeps (ADR 0004) do hold the design rules. Rejected for two reasons: the application-ownership rule is a substring test over twelve file names, so a thirteenth module escapes it and a permitted substring is a rule that is not there; and the rule's own evidence — `menu`, `feedback` and `artwork` passing it while naming `TrackSort`, `PlaylistId`, `NoticePayload` and `RequestedSize` — shows a sweep grading names rather than dependencies.
- **One crate for the theme and the components together.** Fewer manifests and no chain to state, but it grants the design store a dependency on widget code: every consumer of a token would also take every widget, and the design authority could not be read by anything that does not draw, which is the opposite of what a design system is for.
- **`riff-gui-theme` plus a separate icons crate.** The icon atlas is the one module in the design authority that needs a rasterizer (`resvg`) and holds a texture cache, so it is the one plausible split inside it. Rejected: `theme`, `fonts` and `icons` are one authority — the architecture doc already says they move together — and separating them would leave two places that decide what an icon looks like.
- **Opaque keys rather than a mirrored display vocabulary in the component crate.** Decoupling by erasure — `menu` and `feedback` would take caller-supplied strings and hand back the one that was chosen. Rejected in favour of an explicit display vocabulary: these components are riff-specific rather than general, and a named `SortKey`/`Severity`/`PlaylistKey` states what the surface is for, where an opaque string states only that it is opaque. The cost accepted with it is a transform at the host boundary, in both directions.

## Consequences

- **Neither crate names a `riff-*` crate.** `riff-gui-theme`'s manifest admits `egui` and `resvg`; `riff-gui-components`' admits `riff-gui-theme` and `egui`. That is the boundary: a manifest edge is checked on every line, so `test_no_primitive_names_an_application_owner` is retired as strictly weaker than the compiler, while the shared-handle sweep and the ADR 0004 token sweeps survive — an `Arc<Mutex<_>>` needs no business crate, and the token rules are about values, not imports.
- **The chain is `riff-gui-theme ← riff-gui-components ← riff-gui`,** and `riff-gui` depends on `riff-gui-theme`, `riff-gui-components` *and* `riff-backend`. Neither new crate gains an edge to the backend, nor to the slices, nor to `riff-infra`.
- **`egui` is pinned once.** The 0.35 pin is load-bearing (0.36 silently drops user-loaded textures from the kittest goldens) and it used to live in one manifest with its rationale. Three hand-written pins is three places to forget it, so the pin and the comment move to `[workspace.dependencies]` in the root manifest and all three crates inherit it. Re-exporting `egui` from the theme crate was rejected as a compatibility shim that makes egui's version an implicit contract of a design system.
- **Names and copy are free in both crates.** The rule is one sentence — no business-crate import, and no decision — not a vocabulary ban. `theme`'s `geometry` namespaces are already named after riff surfaces (`playerbar`, `now_playing`, `seek`), and `prompts` carries riff product copy.
- **The display vocabulary is the crate's own, and mirrored on purpose.** `menu` declares its own sort key and id newtypes rather than naming `TrackSort`, `PlaylistId` or `TrackId`, and `riff-gui` owns the transform across the boundary. **The display→business direction is exhaustive with no wildcard**, so the crate can never emit an intent the host cannot answer; the **business→display direction is partial**, so a business enum that grows an option no surface displays does not force a change inside the component crate. The mirror's known cost — a business option that *should* be displayed gets no compile error, only a deliberate edit — is the coupling the split buys out of. *Excluded:* the feedback board stays a frontend module (like `artwork`) rather than joining the mirror — its entire API is `NoticeSource`-shaped, its producer sites are riff's, and the maintainer has ruled out touching it for the foreseeable future.
- **`artwork.rs` stays in `riff-gui`.** Its seams are not names. `COVER_CACHE_CAP` and `lru_insert` are the cover service's own eviction policy, shared with the backend, and `RequestedSize` is a `{w,h}` contract the backend's cover loader consumes too. Importing either would put shared policy and a shared contract *inside* the crate whose rule is that it holds neither; duplicating them would be worse. Its request-size vocabulary is not the component library's to own.
- **The two wrong-way edges are resolved downward.** `styled_font` and `search_ring_stroke` leave `now_playing`/`sidebar` for the theme crate (typography and a palette-derived stroke are the token store's to own), and `ghost_icon_button` leaves `sidebar` for the component crate, beside the `begin_icon_button` it wraps. A primitive reaching into the composite that hosts it stops being possible rather than being swept for.
- **The historical paths are not kept alive.** The moved modules stop existing under `riff_gui::ui`, and call sites — including the ~200 in the root integration suite — are updated rather than served by re-exports: with two crates the *path is the boundary*, and a permanent re-export would leave `riff_gui::ui::theme` and `riff_gui_theme` both meaning the same thing. The source-reading guards cannot be served by a re-export in any case, so the token sweeps and the shared-handle sweep are re-homed with the crates they scan.
- **ADR 0004's consequence moves with the store.** Its text names `crates/riff-gui/src/ui/theme.rs` as the token store; that path is amended when the modules physically move, not before.
