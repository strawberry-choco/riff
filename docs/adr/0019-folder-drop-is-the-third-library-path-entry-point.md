# Folder Drops Are the Third Library Path Entry Point

**Status**: Accepted
**Date**: 2026-10-15

The Library Path fact-set — the path, its Readiness, its Watch State, its running watcher, its rows in the Application Store — had two entry points, both reached from a Settings context: the native folder picker on macOS and Windows, and the validated text input on Linux. A folder dragged from the platform's file manager onto the window is the **third entry point into the same fact-set, and no new registration path in the backend**: the drop's candidates go through the same acceptance the picker result and the typed path go through (exists, is-directory, canonicalize), register through the same `LibraryPaths::register`, and land in the same store rows the App Runtime restores at launch. The per-drop resolution — register, reject, scan, report — is one operation of the Library Path adapter (`resolve_dropped_paths` in `crates/riff-gui/src/ui/app/library_picker.rs`), beside the register function the two Settings flows already use; nothing in `riff-backend` or the store learned about drops, and the adapter's module doc reads three entry points on one flow.

**The divergence between the entry points is deliberate, and it is this record's substance: a drop auto-scans; the picker and the typed path still register without scanning.** A drop is an impatient gesture — "add my music now" — made from the file manager, where no Rescan affordance is under the hand, so each *newly registered* root's scan request leaves with the drop, through the same `Scans` port every other scan starts from; the scan service already ignores a request for a root it is actively scanning, and an already-registered root is a silent no-op, so a re-drop can never trigger a surprise rescan. The picker and typed-path flows run in a Settings context where the Rescan button is on screen, so indexing stays the listener's choice there. Feedback rides the structured board, not a new surface: rejections use the standard sentences ("Not a directory: …" and its siblings), and success reports "Added library path, scanning…" on the Library notice — the titlebar's scan slot — so live scan progress overwrites the confirmation moments later. One slot, no new surface.

**The frame protocol carries the fact, and the hover overlay only paints it.** Dropped paths ride `FrameInput` (`crates/riff-gui/src/ui/frame.rs`), read once per frame from the context's dropped files — which is why `FrameInput` lost its `Copy` derive: several folders ride one gesture, and the input is only ever passed by reference. A non-empty drop becomes a `FrameOutput` decision (the decision IS the carry), decided headlessly per the frame protocol's discipline, and enacted at the frame tail — where the folder picker is already performed — with the Library Session locked once. While a drag hovers the window, the veil in `crates/riff-gui/src/ui/drop_overlay.rs` is **draw-half paint and nothing more**: it reads egui's own `hovered_files`, shows for any hovered payload, makes no frame decision, and stores nothing between frames — nothing acts on a hover, so nothing decides one, and the vanish on leave or cancel is next-frame free.

**No platform conditional was added.** The drop arrives through the windowing system on all three platforms — X11 via XDND, Wayland via the data-control support in the pinned winit line, compositor-dependent — with no native-dialog dependency, so the native-picker platform split (product decision 005: native folder picker on macOS/Windows, text input on Linux) stays exactly as it was, and the Linux typed-path flow remains the fallback where a compositor does not deliver drops.

## Considered Options

- **A drop-specific registration path in the backend.** A second application-side operation that owns "drop" facts beside the Library Path module. Rejected: the drop needs no fact the module does not already own — the same acceptance, the same `register`, the same `Scans` port — so a second path would be two behaviours to keep in step, and the one fact-set would quietly become two.
- **Uniform scan semantics: every entry point auto-scans, or none does.** Making the picker and the typed path scan would take the indexing decision away from the one context that has Rescan on screen; making the drop wait for a Rescan that is nowhere in reach strands the impatient gesture it exists for. The entry points differ in context, so they differ in what happens right after registration — the divergence is the point, not drift to be converged later.
- **Probing each hovered payload for is-directory behind the overlay.** The overlay would then only show for genuine folder drags. Rejected: filesystem IO on the frame path, the acceptance already refuses a non-directory at drop time, and the overlay's job is to say "the whole window will take the drop", not to grade the payload.
- **Per-panel drop targets** (drop-on-playlist and friends). Rejected for now: an aiming problem the whole-window target does not have, and a second decision vocabulary the acceptance does not need. Deliberately deferred, not forgotten.
- **A platform conditional around drop support.** Rejected: the drop needs no native dialog, so there is nothing to gate — gating it would have added a fourth Linux-special surface to verify for no behavioural difference on any platform.

## Consequences

- **`FrameInput` is no longer `Copy`.** Several folders ride one gesture and the struct is only ever passed by reference; tests that build it as struct literals are unaffected, and the frame suite asserts the decision on `FrameOutput` with no egui context.
- **A dropped root is indistinguishable from a picked one, except in when its first scan starts.** Same store rows, same Watch State default (Disabled — following a root remains a separate Settings choice, available on a dropped root like any other), same restore at launch, same removal semantics. Overlapping roots bring no new policy: tracks are keyed by full path, so nested drops collapse to one row per file.
- **The hover overlay is verified manually.** It is paint with no decision half, so the frame suite has nothing to assert about it; a golden would need headless hover-input injection, which the pinned egui does not offer today. Its every design value is a token in `riff-gui-theme` (`geometry::drop_overlay`'s 4px inset among them), so the token sweeps hold it.
- **Wayland delivery is compositor-dependent, and that is recorded rather than worked around.** Some compositors do not deliver drops; no Wayland-specific code exists to maintain or remove, and the typed-path flow stays the always-available fallback.
- **Dropping an audio file is a rejection, not a silent nothing.** The standard "Not a directory: …" sentence answers it on the Library notice, and the rest of a mixed drop still registers. Playing or enqueueing a dropped file is deliberately deferred to its own follow-up issue in the tracker.
