# Release and Packaging

This document describes how riff is built for distribution today and how releases could be produced and packaged in the future. It is split into **Current State**, which reflects the verified repository configuration, and **Recommendations**, which are clearly marked suggestions that are not yet implemented. For the development build workflow and profiles, see [development-setup.md](./development-setup.md).

riff is a Cargo workspace that compiles to a single standalone binary (the `riff` binary in `riff-gui`). It has no feature flags, no runtime plugin system, and no external assets that must ship alongside the executable, which keeps packaging straightforward: in principle, distributing riff means distributing one binary per platform.

## Current State

### Release profile

The release build is configured in the root `Cargo.toml` (workspace-level, so it applies to every member) for maximum optimization and a small binary:

```toml
[profile.release]
opt-level = 3
lto = true
codegen-units = 1
strip = true
```

- `opt-level = 3` — full optimizations.
- `lto = true` — link-time optimization across all crates for whole-program optimization.
- `codegen-units = 1` — a single codegen unit, which gives the optimizer the most visibility at the cost of parallelism.
- `strip = true` — debug symbols are stripped from the final binary.

### Build command

Produce a release binary with:

```bash
cargo build --release -p riff-gui
```

The resulting binary is written to `target/release/` (for example `target/release/riff` on Linux/macOS or `target/release/riff.exe` on Windows).

### Binary characteristics

- **Single standalone binary.** riff links its dependencies statically into one executable; there is no separate runtime or library to install.
- **One workspace, one shipped artifact.** The workspace splits the backend into capability crates, but only `riff-gui` produces a binary (the `riff` package target); the other members are libraries, so there is no multi-artifact assembly.
- **No feature flags.** Every build includes the same set of capabilities; the only conditional compilation is per-target-OS for system integration (tray icon and native file dialogs on non-Linux platforms).
- **Stripped.** Debug symbols are removed, reducing binary size.

### MSRV

The crate declares `rust-version = "1.92"`. This documents the intended minimum compiler and matches the `msrv` setting in `clippy.toml`. It is informational only and is not enforced by any CI job.

### Current release process

Releases are currently produced **manually**. There is no CI pipeline, no automated release workflow, and no packaging step. A release today means: bump the version, run `cargo build --release` on the target machine, and distribute the resulting binary by hand. There are no published artifacts, tags, or installers generated by automation.

## Recommendations

Everything below is a suggestion for future work and is **not yet implemented**. Items are grouped by theme.

### Versioning

- Bump the `version` field in `Cargo.toml` (currently `0.1.0`) as part of each release, following semantic versioning. Consider tagging the corresponding commit in git so releases are traceable.

### Release automation

- Add a basic release CI workflow that builds per-OS binaries (Windows, macOS, Linux) on a tag push and uploads them to GitHub Releases. This replaces the manual "build on my machine" step and gives users downloadable artifacts.
- Consider [`cargo-dist`](https://opensource.axo.dev/cargo-dist/), which automates cross-platform binary builds, installers, and release publishing from a Cargo project, reducing the amount of bespoke CI to maintain.

### Platform packaging and signing

- **macOS:** Distributing outside the App Store typically requires code signing and notarization so that Gatekeeper does not block the app. Plan for an Apple Developer ID certificate and the `notarytool`/`stapler` workflow.
- **Windows:** Unsigned binaries trigger SmartScreen warnings. Consider code-signing with a trusted certificate to improve user trust, and decide whether to ship a plain `.exe`, an installer, or a portable zip.
- **Linux:** There is no single packaging standard, but common options include an AppImage (portable, runs on most distributions) and a `.deb` package (for Debian/Ubuntu). Note that Linux builds require ALSA development libraries at compile time; the CI build environment must provide them.

### Suggested order of adoption

1. Add version tagging plus a minimal CI workflow that builds the three platform binaries on tag push.
2. Publish those binaries to GitHub Releases.
3. Evaluate `cargo-dist` to consolidate and simplify the pipeline.
4. Layer on signing and notarization (Windows and macOS) and distribution-specific packaging (Linux) as the user base warrants.
